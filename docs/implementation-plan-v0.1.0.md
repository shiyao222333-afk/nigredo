## 三、Phase 1: 三项验证（详细方案）

### 验证#1: 控件树侦查（最关键）

**目的**：搞清楚你的企微 5.x 的控件结构到底长什么样

**怎么做**：我写一个 Python 侦查脚本，你运行后它自动：
1. 找到企微窗口
2. 把整个控件树打印到文本文件
3. 特别标记是否有 CChatCtrl / QWidget 等关键类名

**成功标准**：
- ✅ 找到 CChatCtrl 或类似消息容器类名 → **路线A可行，进入验证#3**
- ✅ 找到 QWidget 但没有 CChatCtrl → **尝试 QWidget 穿透，进入验证#3**
- ❌ 控件树完全空白（只有 WeWorkWindow 一个节点）→ **路线A失败，跳到验证#2**

**成功后怎么做**：
→ 直接进入验证#3，用找到的类名尝试读取消息

**失败后怎么做**：
→ 跳过验证#3，直接进入验证#2（键盘快捷键），最终走路线B

---

### 验证#2: 键盘快捷键验证

**目的**：确认 Ctrl+1（消息tab）、Ctrl+F（搜索）在你的企微版本能工作

**怎么做**：我写一个测试脚本，你运行后它自动：
1. 激活企微窗口
2. 按 Ctrl+1，截图看是否切到消息tab
3. 按 Ctrl+F，截图看是否弹出搜索框
4. 把结果存到文件

**成功标准**：
- ✅ Ctrl+1 切到消息tab + Ctrl+F 弹出搜索框 → **路线B可行**
- ❌ 快捷键无效 → **路线B失败，只能走路线C（OCR）**

**成功后怎么做**：
→ 路线B确认可行。如果验证#1也成功，优先走路线A；否则走路线B

**失败后怎么做**：
→ 只有路线C（OCR截图）可选，开发量大但技术可行

---

### 验证#3: 消息读取验证（只有验证#1成功才做）

**目的**：确认能不能从消息容器中读取每条消息的发送人和内容

**怎么做**：基于 wx_work_auto 的 t1.py 代码，写一个读取脚本，你运行后它自动：
1. 用验证#1找到的类名定位消息容器
2. 遍历容器内的所有子控件
3. 尝试提取每条消息的：发送人、消息内容、时间
4. 把结果打印出来

**成功标准**：
- ✅ 能提取到发送人 + 消息内容 → **路线A完全可行！直接走路线A**
- ⚠️ 能找到控件但读不到文本内容 → **路线A部分可行，需要路线B补充**
- ❌ 控件存在但子控件完全不可遍历 → **路线A失败，走路线B**

**成功后怎么做**：
→ 路线A确认！进入 Phase 3 实现完整功能

**失败后怎么做**：
→ 退回路线B（键盘+剪贴板方案）

## 四、Phase 2: 方案决策矩阵

| 验证#1 | 验证#2 | 验证#3 | 选哪条路线 | 理由 |
|:------:|:------:|:------:|:---------:|------|
| ✅ | 任意 | ✅ | **路线A** | 能直接读控件，最精准最高效 |
| ✅ | ✅ | ❌ | **路线B** | 控件能找到但读不到内容，用键盘操作+剪贴板提取 |
| ❌ | ✅ | — | **路线B** | 控件树不可用，但快捷键能用 |
| ❌ | ❌ | — | **路线C** | 只能OCR截图，开发量最大但兜底可行 |
| ✅ | ✅ | ⚠️ | **路线A+B混合** | 控件定位+键盘操作，取长补短 |

### 三条路线详解

#### 路线A: UIA直达（最理想）

```
企微窗口 → find_elements(进程ID, CChatCtrl) → 遍历消息列表 → 提取文本 → 通知
```

- **原理**：直接从控件树读取消息内容，不模拟任何人工操作
- **优势**：精准、快速、不干扰用户使用企微
- **风险**：企微版本更新可能改类名，需要维护
- **开发量**：中（约3-5天）
- **参考代码**：wx_work_auto test/t1.py 的 get_real_content() + get_unread_messages()

#### 路线B: 键盘+剪贴板（最稳定）

```
Ctrl+1(消息tab) → Ctrl+F(搜索) → 输入群名 → 回车(进入聊天)
→ Ctrl+A(全选消息) → Ctrl+C(复制到剪贴板) → 读取剪贴板 → 解析消息
```

- **原理**：用键盘快捷键操作企微，用剪贴板提取消息文本
- **优势**：不依赖控件树结构，只要快捷键不变就能用
- **风险**：操作时会抢焦点（干扰用户），剪贴板内容格式需要解析
- **开发量**：中（约3-5天）
- **参考代码**：wx_work_auto main.py 的 send_message() 组合键逻辑

#### 路线C: OCR截图（最后手段）

```
定时截图企微窗口 → OCR识别文字 → 正则提取消息 → 坐标定位点击
```

- **原理**：完全通过屏幕截图+文字识别，不碰控件树
- **优势**：对企微版本变化最不敏感
- **风险**：OCR精度有限、实时性差（每轮2-3秒）、受分辨率影响
- **开发量**：高（约5-8天）
- **参考代码**：wx_work_auto test/t3.py 的图像识别逻辑 + EasyOCR

## 八、你需要注意的

1. **验证阶段需要你配合**：脚本需要你的电脑上运行，因为企微在你电脑上
2. **企微版本很重要**：请先确认你的企微版本号（企微→设置→关于）
3. **验证阶段不影响正常使用**：脚本只读不写，不会发消息不会改东西

5. **路线B是保底解**：即使A失败，B几乎一定能工作（影刀就是用类似方式）

## 九、验证#1 结果修正 — 路线A"假死"分析 (2026-06-30)

### 验证#1 实际结果

| 项目 | 结果 |
|------|------|
| 企微版本 | 5.0.9.6029 |
| 控件总数 | 仅 3 个（WeWorkWindow/TitleBarWindow/PerryShadowWnd） |
| CChatCtrl | 未找到 |
| QWidget | 未找到 |
| find_elements | 全空 |
| uiautomation 库 | 0 个二级子控件 |

### 关键发现：路线A 并未彻底失败

**原判断**：DirectUI 在 5.x 比 4.x 更封闭 → 路线A 彻底失败

**修正判断**：企微使用"无障碍客户端检测"机制，pywinauto/uiautomation 库不被认可为合规 UIA 客户端，但 .NET UIAutomationClient.dll 构建的客户端可能触发企微暴露完整控件树。

**技术原理**（来源：微信 4.1.5.16 UIA 检测机制研究，2026-03）：
- 企微/微信不完全屏蔽 UIAutomation，而是检测"谁来敲门"
- 检测到合规 UIA 客户端（引用 UIAutomationClient.dll + UIAutomationTypes.dll 并附着窗口）→ 暴露完整控件树
- 检测到 pywinauto/uiautomation 库 → 不认可，只露 3 个空壳
- 检测到讲述人等屏幕阅读器 → 临时暴露（不稳定）

**影刀的佐证**：影刀有专门的"获取企业微信聊天记录"指令，能直接读取群聊消息，证明技术上完全可行。

### 修正后的路线方案

| 路线 | 原理 | 可行性 | 耗时 |
|------|------|--------|------|
| **路线A+** (新) | C# 构建 .NET UIA 客户端，触发企微暴露控件树 | 高（有微信成功案例） | 2-3 天 |
| 路线B (原) | 键盘快捷键 + 剪贴板 | 中高 | 3-5 天 |
| 路线C (原) | OCR 截图 | 低优先级 | 5-8 天 |
| **路线D** (新) | 直接读企微进程内存 | 中（需逆向） | 5-8 天 |

### 快速验证方案（5 分钟，零风险）

**目的**：验证"门卫"理论是否正确

**步骤**：
1. 启动 Windows 讲述人（Win+Ctrl+Enter）
2. 保持讲述人运行，双击 `run_verify_01.bat`
3. 查看报告——如果控件从 3 个变成几十/几百个 → 理论验证成功
4. 关闭讲述人（Win+Ctrl+Enter）

**成功**：路线A+ 确认可行，用 C# 构建 UIA 客户端
**失败**：企微 5.x 可能用了更严格的检测，退回路线B
